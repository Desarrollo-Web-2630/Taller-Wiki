1. Objetivo y estrategia

Procesos del modelador BPMN a automatizar: los flujos que un usuario hace de punta a punta en el navegador:

  • Iniciar y cerrar sesión con JWT, y protección de rutas sin sesión.
  • Crear procesos, validar el formulario, rechazar nombres repetidos y buscar en el listado paginado.
  • Modelar en el editor: arrastrar el pool de la empresa, una lane, actividades, conectarlas con un arco y mover una actividad con drag and drop, comprobando que todo queda guardado al recargar.
  • Control de acceso: rol LECTURA en solo lectura y aislamiento de la información entre empresas.

Tipos de pruebas: UI, API, integración, extremo a extremo:

  • Extremo a extremo (sistema): 14 casos con Selenium WebDriver sobre la aplicación completa (Chrome → Angular → API REST → Spring Security → JPA).
  • Integración de API: 22 casos de SeguridadIntegracionTest con la cadena real de Spring Security sobre H2, más los tests de controladores con MockMvc.
  • Unitarias: servicios, DTO y modelo del backend (401 pruebas en total con las de integración) y 17 pruebas del frontend (interceptor, guards y servicios) con Jasmine y Karma.
  • API manual: colección de Postman. Carga: JMeter (documento 04).

Herramientas y versiones: Selenium WebDriver 4.53.0 para Java (Selenium Manager descarga el chromedriver de Chrome 157), JUnit 5 y AssertJ de Spring Boot 3.3.2, Maven Surefire 3.2.5, Java 21 (compila a 17), Angular 20.3 con Jasmine 5.9 y Karma 6.4, Node 24.21 y JMeter 5.6.2. Se eligió WebDriver en código y no Selenium IDE: el IDE sigue en beta desde 2024 y graba localizadores frágiles, y el editor usa drag and drop nativo de HTML5, que ni el IDE ni las Actions de WebDriver disparan. Con código se resolvió con un helper, Page Objects y datos controlados.

2. Diseño de suites

Estructura de archivos y suites: todo en thymeleaf/src/test/java/com/proyecto1/thymeleaf/e2e (repositorio Proyecto1), marcado con @Tag("e2e"). En el inventario, las rutas son relativas a thymeleaf/src/test/java/com/proyecto1/thymeleaf:

  • E2EBase: arranca el backend, prepara los datos y abre y cierra Chrome en cada prueba.
  • Page Objects: PaginaLogin, PaginaProcesos, PaginaFormularioProceso y PaginaEditor; las pruebas no tocan selectores directamente.
  • Utilidades: ArrastrarYSoltar (drag and drop HTML5) y EvidenciaE2E (captura de pantalla al final de cada caso).
  • Suites: AutenticacionE2ETest (4 casos), ProcesosE2ETest (4), EditorProcesoE2ETest (2) y ControlAccesoE2ETest (4).

Casos priorizados: alta: E2E-01, 03, 09, 10, 11, 13 y 14 (seguridad, aislamiento y núcleo del editor); media: E2E-02, 04, 05, 06, 07 y 12 (errores, validaciones y guards); baja: E2E-08 (búsqueda).

Preparación y limpieza de datos: la prueba arranca el backend con @SpringBootTest en el puerto 8080 y perfil h2, así que cada corrida empieza con una base en memoria nueva y se borra sola al terminar. Antes de cada caso se crean, solo si faltan, el usuario lector@demo.com (LECTURA), la empresa «Otra Empresa SAS» con su administrador y un proceso privado, y un rol de proceso. Las pruebas que crean datos usan nombres únicos, así no dependen del orden. Cada caso abre un Chrome nuevo, sin sesión ni token.

Identificadores / selectores y estabilidad de scripts:

  • Se agregaron atributos data-testid al frontend (login-correo, fila-proceso, paleta-ACTIVIDAD, tablero, actividad, arco, dialogo-guardar…), que no cambian con estilos ni textos.
  • Solo esperas explícitas (WebDriverWait de 10 s, ningún Thread.sleep) y tolerancia a StaleElementReferenceException, porque Angular vuelve a pintar listas y nodos.
  • El drag and drop se simula con los eventos reales del navegador (dragstart, dragover, drop) y deja correr un ciclo de detección de cambios de Angular entre ellos; las posiciones se calculan respecto al lienzo.
  • El caso de mover una actividad verifica la nueva posición en la base de datos y otra vez en pantalla tras recargar.

3. Ejecución

Comandos para ejecutar suites:

  1. Frontend (otra terminal): cd front, npm ci y npx ng serve (queda en http://localhost:4200).
  2. Suite E2E completa: cd thymeleaf y ./mvnw test -Pe2e (el backend lo arranca la propia prueba).
  3. Una sola suite: ./mvnw test -Pe2e -Dtest=EditorProcesoE2ETest. Ver el navegador: -De2e.headless=false.
  4. Unitarias e integración del backend: ./mvnw test (excluye las E2E). Frontend: npx ng test --watch=false --browsers=ChromeHeadless.

Ejecución local y en integración continua (CI): se ejecutó en local en Windows 10 con Chrome 157 en modo headless. El pipeline actual de GitHub Actions (deploy.yml) construye y publica la imagen sin correr pruebas (-DskipTests), así que hoy ninguna suite corre en CI. Queda propuesto un job en ubuntu-latest, que ya trae Chrome, que ejecute ./mvnw test, levante ng serve en segundo plano, ejecute ./mvnw test -Pe2e y publique target/e2e/capturas como artefacto.

Configuración y variables requeridas: propiedades e2e.headless (true por defecto) y e2e.front (http://localhost:4200). La prueba fija en el backend server.port=8080, app.demo.admin-password, app.jwt.secret, app.cors.origenes=http://localhost:4200 y app.mail.enabled=false. Requisitos: Chrome instalado, puerto 8080 libre, Node y Angular CLI, e internet la primera vez para que Selenium Manager descargue el chromedriver.

Frecuencia de ejecución: antes de cada merge a main y antes de cada entrega o despliegue, en local. Las unitarias y de integración se corren también al hacer el análisis de SonarQube (./mvnw verify sonar:sonar).

4. Resultados

Casos ejecutados, aprobados y fallidos: E2E: 14 ejecutados, 14 aprobados y 0 fallidos en las tres últimas corridas (22/11/2026); la última se hizo sobre main ya integrado con los cambios de seguridad del equipo. Backend: 401 de 401. Frontend: 17 de 17.

Duración de ejecución: suite E2E: entre 75 y 107 s de pruebas (95 a 130 s contando compilación y arranque de Spring). Por suite: Autenticación 29-58 s (incluye el arranque del backend), Procesos 15-18 s, Editor 17-18 s y Control de acceso 13-14 s. Backend completo: 101 s con las 401 pruebas.

Fallos recurrentes e intermitentes: en la primera corrida fallaron E2E-05 y E2E-08 por sincronización: la prueba leía la tabla mientras Angular la volvía a pintar (lista vacía y StaleElementReferenceException). La captura mostraba la aplicación funcionando bien, así que el fallo era de la prueba. Se corrigió la espera y las tres corridas siguientes dieron 14 de 14, sin fallos intermitentes.

Evidencias: logs, video, reportes, capturas: una captura automática por caso (target/e2e/capturas, copiadas a evidencias/selenium), reportes XML y TXT de Surefire (target/surefire-reports) y el log de Maven de cada corrida.

5. Mantenimiento y cierre

Criterios de aceptación: 100 % de las E2E aprobadas en corridas seguidas, también sobre el código integrado; ningún caso depende de otro ni del orden; cada caso deja evidencia; el build normal sigue en verde (401 de 401) sin necesitar navegador.

Acciones correctivas y responsables:

  • Corregir la espera de la búsqueda en PaginaProcesos (Héctor Estrada, hecho).
  • DEF-01: el lienzo vacío en solo lectura invita a arrastrar desde la paleta (equipo de frontend, pendiente).
  • Agregar el job E2E a GitHub Actions (equipo, pendiente).
  • Ampliar la suite a gateways, mensajes entre pools y reordenar lanes (equipo, pendiente).

Mantenimiento de scripts: si cambia una pantalla se actualiza su Page Object, no las pruebas. Los data-testid no se borran sin actualizar la suite. PaginaEditor repite dos constantes del lienzo de Angular (DESPLAZAMIENTO_X = 180 y ANCHO_ACTIVIDAD = 140): si cambian allá, hay que cambiarlas aquí. La versión de Selenium se actualiza en la propiedad selenium.version del pom.xml.

Conclusiones: la suite prueba el sistema completo como lo usa una persona, incluido lo más difícil de automatizar (el drag and drop del editor) y lo más crítico (seguridad multiempresa). Es estable (tres corridas seguidas sin fallos), rápida (menos de 2 minutos) y no afecta el build normal.

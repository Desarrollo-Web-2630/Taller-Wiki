1. Objetivo y estrategia

Procesos del modelador BPMN a automatizar: automatizamos lo que hace una persona en el navegador de principio a fin:

  • Iniciar y cerrar sesión, y que las páginas internas no abran sin sesión.
  • Crear procesos, las validaciones del formulario, el error por nombre repetido y la búsqueda.
  • Modelar en el editor: arrastrar el pool, una lane y actividades desde la paleta, unirlas con un arco y mover una actividad, revisando que todo siga ahí al recargar la página.
  • Permisos: que el rol de lectura no pueda editar y que una empresa no vea los procesos de otra.

Tipos de pruebas: UI, API, integración, extremo a extremo: el foco de este documento son las pruebas de extremo a extremo, pero el proyecto tiene varias capas:

  • Extremo a extremo: 14 casos con Selenium WebDriver sobre la aplicación completa, desde el navegador hasta la base de datos.
  • Integración de la API: los 22 casos de SeguridadIntegracionTest, que usan la configuración real de Spring Security, y las pruebas de los controladores con MockMvc.
  • Unitarias: 401 pruebas en el backend (contando las de integración) y 17 en el frontend con Jasmine y Karma.
  • Además, la colección de Postman para probar la API a mano y JMeter para la carga (documento 04).

Herramientas y versiones: Selenium WebDriver 4.53.0 para Java, que descarga solo el driver del Chrome instalado (Chrome 157), JUnit 5 y AssertJ (los que trae Spring Boot 3.3.2), Maven Surefire 3.2.5 y Java 21. En el frontend, Angular 20.3 con Jasmine 5.9 y Karma 6.4. Elegimos escribir las pruebas con WebDriver y no grabarlas con Selenium IDE por dos razones: el IDE lleva en beta desde 2024 y graba selectores que se rompen fácil, y el editor usa el drag and drop nativo de HTML5, que el IDE no logra reproducir. Con código pudimos resolverlo con un método propio.

2. Diseño de suites

Estructura de archivos y suites: todas las pruebas están en thymeleaf/src/test/java/com/proyecto1/thymeleaf/e2e (repositorio Proyecto1) y llevan la etiqueta e2e. En el inventario de abajo las rutas empiezan desde thymeleaf/src/test/java/com/proyecto1/thymeleaf.

  • E2EBase arranca el backend, prepara los datos y abre y cierra Chrome en cada prueba.
  • Una clase por pantalla (PaginaLogin, PaginaProcesos, PaginaFormularioProceso y PaginaEditor), siguiendo el patrón Page Object. Así las pruebas no dependen directamente de los selectores.
  • ArrastrarYSoltar hace el drag and drop y EvidenciaE2E guarda una captura al final de cada caso.
  • Cuatro suites: AutenticacionE2ETest (4 casos), ProcesosE2ETest (4), EditorProcesoE2ETest (2) y ControlAccesoE2ETest (4).

Casos priorizados: dimos prioridad alta a la seguridad y al editor (E2E-01, 03, 09, 10, 11, 13 y 14). Los mensajes de error, las validaciones y los permisos de rutas quedaron en prioridad media (E2E-02, 04, 05, 06, 07 y 12), y la búsqueda en baja (E2E-08).

Preparación y limpieza de datos: la propia prueba levanta el backend en el puerto 8080 con la base H2 en memoria, así que cada corrida empieza limpia y no queda basura al terminar. Antes de cada caso se crean, si no existen, un usuario de solo lectura, una segunda empresa con su administrador y un proceso privado, y un rol de proceso. Las pruebas que crean procesos les ponen nombres únicos para no depender del orden, y cada caso abre un Chrome nuevo, sin sesión.

Identificadores / selectores y estabilidad de scripts:

  • Agregamos atributos data-testid en el frontend (login-correo, fila-proceso, paleta-ACTIVIDAD, tablero, actividad, arco, dialogo-guardar, entre otros), que no cambian si se cambia el diseño o los textos.
  • Solo usamos esperas explícitas de hasta 10 s, nunca pausas fijas, y reintentamos cuando Angular vuelve a dibujar un elemento (StaleElementReferenceException).
  • Las acciones de Selenium no disparan el drag and drop de HTML5, así que lanzamos los mismos eventos que el navegador (dragstart, dragover y drop), dejando que Angular actualice la pantalla entre uno y otro.
  • En la prueba de mover una actividad revisamos la nueva posición en la base de datos y otra vez en pantalla después de recargar.

3. Ejecución

Comandos para ejecutar suites:

  1. En otra terminal, levantar el frontend: cd front, npm ci y npx ng serve (queda en http://localhost:4200).
  2. Correr todas las pruebas E2E: cd thymeleaf y ./mvnw test -Pe2e. El backend lo arranca la misma prueba.
  3. Correr una sola suite: ./mvnw test -Pe2e -Dtest=EditorProcesoE2ETest. Para ver el navegador mientras corre, agregar -De2e.headless=false.
  4. Las unitarias y de integración se corren con ./mvnw test, que deja fuera las E2E. Las del frontend, con npx ng test --watch=false --browsers=ChromeHeadless.

Ejecución local y en integración continua (CI): por ahora las corremos en local, en Windows 10 con Chrome sin ventana. El pipeline de GitHub Actions (deploy.yml) construye y publica la imagen con -DskipTests, o sea que hoy no corre ninguna prueba. Lo que proponemos es agregar un job en ubuntu-latest, que ya trae Chrome, que corra ./mvnw test, levante el frontend, corra ./mvnw test -Pe2e y guarde las capturas como artefacto.

Configuración y variables requeridas: se pueden cambiar dos propiedades: e2e.headless (true por defecto) y e2e.front (por defecto http://localhost:4200). La prueba configura el backend sola: puerto 8080, contraseña del admin de demo, clave del JWT, CORS para el frontend y correo desactivado. Hace falta tener Chrome, el puerto 8080 libre, Node con Angular CLI e internet la primera vez, para que Selenium descargue el driver.

Frecuencia de ejecución: antes de cada merge a main y antes de cada entrega o despliegue. Las unitarias y de integración también corren cada vez que hacemos el análisis de SonarQube (./mvnw verify sonar:sonar).

4. Resultados

Casos ejecutados, aprobados y fallidos: los 14 casos pasaron en las últimas cuatro corridas del 22 de noviembre. Las dos últimas se hicieron sobre main ya integrado con los cambios de seguridad del resto del equipo. El backend pasa 401 de 401 pruebas y el frontend 17 de 17.

Duración de ejecución: la suite completa tarda entre 75 y 107 s, o entre 95 y 130 s si se cuenta la compilación y el arranque de Spring. La suite de autenticación suele ser la más lenta (de 29 a 58 s) porque es la que arranca el backend; las demás tardan de 13 a 35 s. Las pruebas del backend sin E2E tardan unos 100 s.

Fallos recurrentes e intermitentes: en la primera corrida fallaron E2E-05 y E2E-08. Las capturas mostraban la aplicación funcionando bien: el problema era que la prueba leía la tabla de procesos mientras Angular la estaba volviendo a dibujar. Corregimos la espera y desde entonces no ha vuelto a fallar ninguna prueba.

Evidencias: logs, video, reportes, capturas: cada caso guarda una captura de pantalla al terminar (carpeta evidencias/selenium) y Maven deja los reportes de Surefire. La figura 1 es el reporte de la última corrida y las siguientes son capturas que tomó Selenium durante las pruebas.

5. Mantenimiento y cierre

Criterios de aceptación: todas las E2E tienen que pasar, incluso sobre el código integrado; ningún caso puede depender de otro ni del orden; cada caso tiene que dejar su captura, y el build normal tiene que seguir funcionando (401 de 401) sin necesitar un navegador.

Acciones correctivas y responsables:

  • Corregir la espera de la búsqueda en PaginaProcesos. Héctor Estrada, hecho.
  • DEF-01: en modo solo lectura el lienzo vacío dice que se arrastre desde la paleta, pero ese usuario no tiene paleta. Equipo de frontend, pendiente.
  • Agregar el job de pruebas E2E a GitHub Actions. Equipo, pendiente.
  • Ampliar la suite a gateways, mensajes entre pools y reordenar lanes. Equipo, pendiente.

Mantenimiento de scripts: si cambia una pantalla, se ajusta su Page Object y las pruebas quedan igual. Los data-testid no se deben borrar sin actualizar la suite. PaginaEditor copia dos medidas del lienzo de Angular (DESPLAZAMIENTO_X = 180 y ANCHO_ACTIVIDAD = 140); si cambian allá, hay que cambiarlas aquí. La versión de Selenium se cambia en la propiedad selenium.version del pom.xml.

Conclusiones: con estas pruebas revisamos la aplicación como la usaría una persona, incluyendo lo más difícil de automatizar, que es el drag and drop del editor, y lo más delicado, que es la separación entre empresas. La suite es estable, corre en menos de dos minutos y no afecta el build normal.

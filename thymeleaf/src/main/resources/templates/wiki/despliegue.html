1. Alcance y prerrequisitos

Ambientes disponibles (local, pruebas, producción): el sistema tiene dos repositorios (backend y frontend) que se despliegan por separado. Hay tres ambientes; no existe un ambiente de pruebas aparte, las pruebas automáticas corren en local con H2 antes de hacer merge a main:

  • Local de desarrollo: backend con ./mvnw spring-boot:run y perfil h2 (base en memoria) y frontend con npm start en http://localhost:4200. Sin backend, el frontend se prueba con npm run mock.
  • Local con Docker Compose: cada repositorio trae su docker-compose.yml; el del backend levanta PostgreSQL 16 + API y el del frontend levanta API (perfil h2) + nginx con la SPA en http://localhost:4200.
  • Producción (curso): MicroK8s en una VM de la universidad (10.43.99.75), namespace procesos, desplegado automáticamente con GitHub Actions en cada push a main. En el mismo namespace corre la wiki del proyecto (procesos-wiki), publicada en /wiki.
  • Vitrina en Vercel: solo la landing pública del frontend; no tiene backend, así que el login y lo que llama a /api no funcionan allí.

Infraestructura requerida:

  • VM Ubuntu 22.04.5 LTS en la red de la Javeriana, con mínimo 2 CPU, 4 GB de RAM y 20 GB de disco; acceso por SSH con la VPN conectada (usuario estudiante).
  • MicroK8s 1.30 con los complementos dns, ingress (NGINX Ingress Controller) y hostpath-storage (para el volumen de PostgreSQL).
  • Un runner self-hosted de GitHub Actions instalado en la VM con la etiqueta main (uno a nivel de organización o uno por repositorio).
  • GitHub Container Registry (GHCR) para guardar las imágenes y runners ubuntu-latest de GitHub para construirlas.
  • Recursos reservados en el clúster: backend 200m CPU / 384–768 Mi; frontend 50m / 32–128 Mi por réplica; PostgreSQL 100m / 256–512 Mi y un PVC de 1 Gi.

Dependencias y versiones:

  • Backend: Java 17 (imagen eclipse-temurin:17-jre), Maven 3.9 para compilar, Spring Boot 3.3.2, driver de PostgreSQL y H2.
  • Frontend: Node 22 (alpine) para compilar, Angular 20.3, nginx 1.27-alpine para servir.
  • Base de datos: imagen oficial postgres:16.
  • Despliegue: Docker, MicroK8s 1.30 (kubectl incluido), acciones actions/checkout@v4 y docker/login-action@v3.
  • Local: JDK 17+, Node 22 y npm, Docker Desktop (opcional) y Git.

Accesos y permisos requeridos:

  • VPN de la Javeriana para llegar a la VM y a la aplicación.
  • Cuenta en la VM con sudo; el usuario del runner debe poder ejecutar sudo microk8s sin contraseña (regla en /etc/sudoers.d/microk8s-runner).
  • Administrador de la organización Desarrollo-Web-2630 en GitHub para registrar el runner a nivel de organización (si no, uno por repositorio).
  • Permiso packages: write del workflow para publicar en GHCR (lo da el GITHUB_TOKEN) y un token personal con read:packages para el secret ghcr-secret que usa el clúster para bajar las imágenes.
  • Usuarios de la aplicación: el admin de demo admin@demo.com y los que cada empresa registre (roles ADMIN, EDITOR y LECTURA).

2. Configuración

Variables de entorno (sin divulgar secretos): el backend lee toda su configuración de variables de entorno; ningún valor real se versiona. En el clúster las de credenciales vienen del Secret procesos-secrets y el resto las fija k8s/backend.yaml:

  • Base de datos: DB_HOST (procesos-db), DB_PORT (5432), DB_NAME, DB_USER, DB_PASSWORD (Secret).
  • Seguridad: JWT_SECRET (Secret, mínimo 32 caracteres), JWT_EXPIRACION_MINUTOS (60 por defecto), APP_CORS_ORIGENES (http y https de 10.43.99.75).
  • Datos iniciales: DEMO_ADMIN_PASSWORD (Secret): contraseña del admin de demo que se crea con la base vacía.
  • Correo: APP_MAIL_ENABLED=false en el despliegue; con true se usan MAIL_HOST, MAIL_PORT, MAIL_USERNAME y MAIL_PASSWORD.
  • Enlaces y JVM: APP_BACKEND_BASE_URL y APP_FRONTEND_BASE_URL (http://10.43.99.75), SPRING_JPA_HIBERNATE_DDL_AUTO=update, JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75.
  • Frontend: solo BACKEND_URL (http://procesos-backend:8080), que nginx usa para reenviar /api/.
  • Workflows: NAMESPACE=procesos y DOMINIO=10.43.99.75 en .github/workflows/deploy.yml de cada repositorio.

Configuración de base de datos: PostgreSQL 16 corre en el Deployment procesos-db con estrategia Recreate (dos pods no pueden usar el mismo disco) y guarda los datos en el PVC procesos-db-datos de 1 Gi, montado con PGDATA=/var/lib/postgresql/data/pgdata porque el volumen trae una carpeta lost+found. Nombre, usuario y contraseña salen del Secret. Se expone solo dentro del clúster con el Service procesos-db:5432 y tiene readiness probe con pg_isready. El perfil h2 usa H2 en memoria en modo PostgreSQL, y en Docker Compose local la base es postgres:16 con un volumen pgdata.

Configuración de frontend y backend:

  • Backend: imagen de dos etapas (maven:3.9-eclipse-temurin-17 compila con mvn package -DskipTests; eclipse-temurin:17-jre ejecuta el jar en el puerto 8080). Perfiles: h2, local, postman y sin perfil para despliegue. Readiness probe en /v3/api-docs a los 20 s y liveness a los 120 s; 1 réplica con imagePullPolicy: Always.
  • Frontend: imagen de dos etapas (node:22-alpine ejecuta npm ci y npm run build; nginx:1.27-alpine sirve dist/procesos-front/browser). nginx/default.conf.template reenvía /api/ a ${BACKEND_URL}, redirige las rutas de Angular a index.html y agrega encabezados de seguridad. 2 réplicas con readiness probe en /.
  • Ingress procesos: clase public de MicroK8s, sin host (responde por la IP). /api, /swagger-ui y /v3/api-docs van a procesos-backend:8080 y / a procesos-frontend:80.
  • Los manifiestos usan los marcadores __OWNER__ y __DOMINIO__, que el workflow reemplaza con sed antes de aplicarlos.

Manejo de secretos:

  • Los dos Secrets se crean a mano una sola vez en el servidor y nunca se suben al repositorio: procesos-secrets (DB_NAME, DB_USER, DB_PASSWORD, JWT_SECRET, DEMO_ADMIN_PASSWORD) y ghcr-secret (tipo docker-registry, para bajar las imágenes privadas de GHCR).
  • k8s/secret.example.yaml solo muestra la forma del Secret, con valores CAMBIAR; el workflow no lo aplica.
  • Las contraseñas se generan en el servidor con openssl rand -base64.
  • En GitHub Actions solo se usa el GITHUB_TOKEN automático para publicar en GHCR; no hay secretos propios en los workflows.
  • Si un valor cambia, se reinicia el backend para que lo lea: kubectl rollout restart deployment/procesos-backend.

3. Procedimiento de despliegue

Preparación del entorno

Se hace una sola vez en la VM, con la VPN conectada y por SSH:

sudo apt update && sudo apt -y upgrade
sudo snap install microk8s --classic --channel=1.30/stable
sudo microk8s status --wait-ready
sudo microk8s enable dns ingress hostpath-storage
sudo microk8s kubectl create namespace procesos
echo "estudiante ALL=(ALL) NOPASSWD: /snap/bin/microk8s" | sudo tee /etc/sudoers.d/microk8s-runner
./config.sh --url <url> --token <token> --labels main
sudo ./svc.sh install && sudo ./svc.sh start
sudo microk8s kubectl create secret docker-registry ghcr-secret --docker-server=ghcr.io \
  --docker-username=<usuario_github> --docker-password=<token_read_packages> -n procesos
sudo microk8s kubectl create secret generic procesos-secrets -n procesos \
  --from-literal=DB_NAME=procesos --from-literal=DB_USER=procesos \
  --from-literal=DB_PASSWORD="$(openssl rand -base64 24)" \
  --from-literal=JWT_SECRET="$(openssl rand -base64 48)" \
  --from-literal=DEMO_ADMIN_PASSWORD='<clave del admin demo>'

Construcción / empaquetado

Lo hace el job 1 (build-and-publish) de cada workflow en un runner de GitHub: descarga el código, inicia sesión en GHCR con el GITHUB_TOKEN, construye la imagen con el Dockerfile multietapa y la publica con dos tags: latest y los 7 primeros caracteres del commit, para poder volver a una versión exacta. Las imágenes quedan como ghcr.io/desarrollo-web-2630/procesos-backend y ghcr.io/desarrollo-web-2630/procesos-frontend. En local el mismo empaquetado se prueba con:

cd thymeleaf && docker build -t procesos-backend .
cd front && docker build -t procesos-front .
docker compose up --build

Ejecución de migraciones

El proyecto no usa una herramienta de migraciones (Flyway o Liquibase). En el clúster Hibernate crea y ajusta las tablas al arrancar (SPRING_JPA_HIBERNATE_DDL_AUTO=update), así que el primer despliegue funciona con la base vacía. Con la base vacía, DataInitializer crea la empresa Empresa Demo, el usuario admin@demo.com (activo si se definió DEMO_ADMIN_PASSWORD) y el proceso Solicitud de vacaciones. El valor por defecto de la aplicación es ddl-auto=none, para que nunca modifique una base que no se haya configurado a propósito. Antes de un cambio de modelo que borre o renombre columnas se toma un respaldo con pg_dump (sección 4), porque update solo agrega.

Despliegue de componentes

Lo hace el job 2 (deploy-onpremise) en el runner self-hosted de la VM. Revisa si el Deployment ya existe, reemplaza los marcadores de los manifiestos, los aplica, fuerza rollout restart (con el tag latest el apply no cambia el pod) y espera con rollout status; si un pod no queda listo, el job termina en rojo. El orden importa solo la primera vez, porque nginx del frontend necesita que ya exista el Service del backend:

  1. Push a main de Proyecto1 (o Run workflow en Actions): postgres.yaml + backend.yaml.
  2. Cuando termine en verde, push a main de Proyecto2: frontend.yaml + ingress.yaml.
sed -e "s|__OWNER__|${OWNER_LC}|g" -e "s|__DOMINIO__|${DOMINIO}|g" "$f" \
  | sudo microk8s kubectl apply -n "$NAMESPACE" -f -
sudo microk8s kubectl rollout restart deployment/procesos-backend -n procesos
sudo microk8s kubectl rollout status deployment/procesos-backend -n procesos --timeout=300s

Después del primer despliegue, cada repositorio se despliega solo con su propio push a main.

Verificación posterior al despliegue

El job 2 ya valida que los pods queden listos. Además se comprueba a mano:

sudo microk8s kubectl get pods,svc,ingress,pvc -n procesos
curl -i http://10.43.99.75/
curl -i http://10.43.99.75/api/v1/procesos
curl -i -X POST http://10.43.99.75/api/auth/login -H 'Content-Type: application/json' \
  -d '{"correo":"admin@demo.com","password":"<DEMO_ADMIN_PASSWORD>"}'

En el navegador: http://10.43.99.75 (aplicación) y http://10.43.99.75/swagger-ui.html (API). Estado en el monitor del curso: https://javeriana.inphotech.co/k8smonitor.

4. Operación y recuperación

Comandos de inicio, parada y reinicio:

NS=procesos
sudo microk8s kubectl scale deployment/procesos-backend --replicas=0 -n $NS
sudo microk8s kubectl scale deployment/procesos-backend --replicas=1 -n $NS
sudo microk8s kubectl rollout restart deployment/procesos-backend -n $NS
sudo microk8s stop
sudo microk8s start

Igual para procesos-frontend (2 réplicas) y procesos-db (1 réplica). Las dos últimas líneas detienen y arrancan todo el clúster.

Registros y monitoreo:

sudo microk8s kubectl logs -f deployment/procesos-backend -n procesos
sudo microk8s kubectl describe pod <pod> -n procesos
sudo microk8s kubectl get events -n procesos --sort-by=.lastTimestamp
  • Cada ejecución del workflow queda en la pestaña Actions de cada repositorio, con el log de cada paso.
  • Las readiness y liveness probes sacan del Service y reinician un pod que deja de responder.
  • El monitor del curso (https://javeriana.inphotech.co/k8smonitor) muestra el estado del namespace, los pods y los servicios.
  • Con el correo desactivado, los enlaces de activación de cuenta aparecen en el log del backend.

Estrategia de reversión (rollback): como cada imagen se publica también con el SHA corto del commit, se puede volver a la versión anterior o a una exacta:

sudo microk8s kubectl rollout undo deployment/procesos-backend -n procesos
sudo microk8s kubectl set image deployment/procesos-backend \
  procesos-backend=ghcr.io/desarrollo-web-2630/procesos-backend:<sha7> -n procesos
  • La otra opción es revertir el commit en main (git revert) para que el workflow vuelva a desplegar el código anterior.
  • Si el cambio tocó la base, se restaura el respaldo tomado antes del despliegue.

Respaldo y recuperación: los datos viven en el PVC procesos-db-datos y sobreviven a reinicios y redespliegues del pod; borrar el PVC borra la base. Respaldo y restauración con pg_dump/psql dentro del pod:

sudo microk8s kubectl exec deployment/procesos-db -n procesos -- \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > respaldo_$(date +%F).sql
sudo microk8s kubectl exec -i deployment/procesos-db -n procesos -- \
  sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"' < respaldo_AAAA-MM-DD.sql

Problemas conocidos

  • Job en "Waiting for a runner": el runner está apagado, tiene una etiqueta distinta de main o quedó registrado solo en el otro repositorio.
  • ImagePullBackOff: falta ghcr-secret en el namespace o el paquete de GHCR es privado.
  • CreateContainerConfigError: falta el Secret procesos-secrets o una de sus claves.
  • Backend en CrashLoopBackOff: casi siempre la conexión a la base o un JWT_SECRET de menos de 32 caracteres; revisar los logs.
  • procesos-db en Pending: no se creó el PVC porque falta microk8s enable hostpath-storage.
  • Frontend en CrashLoopBackOff (host not found in upstream): se desplegó antes que el backend.
  • 404 o 503 desde el Ingress: el Ingress no existe (falta desplegar el frontend) o los pods aún no están listos.
  • El sitio sigue con el código viejo: el job no corrió rollout restart, necesario con el tag latest.
  • Aviso "Node.js 20 is deprecated" en Actions: es una advertencia de GitHub sobre las acciones checkout y docker/login; no hace fallar el despliegue. Se resuelve actualizando esas acciones a sus versiones más recientes.
  • Limitaciones aceptadas: la aplicación se sirve por HTTP sin TLS (solo dentro de la VPN), no hay herramienta de migraciones y PostgreSQL es una sola instancia, así que un cambio en la base implica una caída corta.

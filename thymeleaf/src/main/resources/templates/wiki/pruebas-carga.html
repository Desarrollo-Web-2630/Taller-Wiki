1. Objetivo y alcance

Objetivo medible de la prueba: comprobar que la API REST del editor atiende 100 usuarios concurrentes autenticados con JWT con un p95 de hasta 500 ms por operación y menos de 1 % de errores, y encontrar dónde empieza a degradarse el rendimiento con una prueba de estrés de 200 usuarios.

Flujos BPMN o endpoints que serán evaluados: el recorrido de un usuario que entra, consulta sus procesos, crea uno y trabaja en el editor:

  • POST /api/auth/login: una vez por usuario virtual; el JWT viaja luego en el encabezado Authorization.
  • GET /api/v1/procesos (listar) y GET /api/v1/procesos/buscar?page=0&size=10 (búsqueda paginada).
  • POST /api/v1/procesos (crear proceso) y GET /api/v1/procesos/{id} (detalle del proceso creado).
  • GET /api/v1/procesos/{id}/actividades: carga del lienzo del editor BPMN.
  • POST /api/v1/procesos/{id}/actividades/{actividadId}/mover: guarda el drag and drop de una actividad.

Ambiente y características de infraestructura: ejecución local, con el generador de carga y el servidor en el mismo equipo.

  • Equipo: portátil con Windows 10 Pro, Intel Core i7-4702MQ (4 núcleos, 8 hilos, 2,2 GHz) y 7,8 GB de RAM.
  • Backend: Spring Boot 3.3.2 con Tomcat embebido, Java 21.0.10, ejecutado como jar con -Xmx1g y perfil h2 (base H2 en memoria en modo PostgreSQL). En este equipo no había Docker ni PostgreSQL; en producción la aplicación usa PostgreSQL 16 sobre Kubernetes.
  • Generador: JMeter en la misma máquina, así que compite por CPU con el backend (ver cuellos de botella).

2. Escenarios y criterios

Usuarios concurrentes esperados: el escenario objetivo es de 100 usuarios simultáneos (E3), por encima del uso esperado de una empresa pequeña o de un curso. También se midieron 20 (base), 50 (media) y 200 usuarios (estrés, el doble del objetivo).

Patrón de incremento de carga: rampa lineal: los usuarios arrancan repartidos durante 10, 20, 30 y 20 s. Cada usuario hace login una sola vez y luego repite 10 veces el ciclo de seis operaciones, con una pausa aleatoria de 100 a 300 ms entre acciones. E4 mete 200 usuarios en 20 s para provocar un pico.

Duración de cada escenario: medida por JMeter desde la primera hasta la última petición: E1 24,6 s, E2 33,4 s, E3 43,5 s y E4 38,8 s, con entre 1.226 y 12.206 peticiones por escenario (22.594 en total).

Umbrales de aceptación definidos por el equipo:

  • p95 de hasta 500 ms en cada operación de negocio; hasta 1.000 ms en el login, que usa BCrypt y es lento a propósito.
  • Tasa de errores menor al 1 % (respuesta distinta de 200/201 o aserción fallida).
  • CPU promedio del backend por debajo del 70 %.
  • E3 (objetivo) debe cumplirlos todos; E4 es exploratorio y sirve para ubicar el límite.

3. Preparación y ejecución

Herramienta empleada y versión: Apache JMeter 5.6.2, ejecutado con jmeter-maven-plugin 3.8.0 (Maven lo descarga, no hay que instalarlo), con el reporte HTML del propio JMeter. CPU y memoria medidas con un script de PowerShell que lee el proceso Java del backend una vez por segundo.

Datos de prueba utilizados: usuario admin@demo.com (rol ADMIN de «Empresa Demo»), creado por el inicializador de datos con la contraseña de la variable DEMO_ADMIN_PASSWORD. Un hilo de preparación (setUp Thread Group) crea por API un rol de proceso, el proceso «Editor carga», su pool de la empresa, una lane y una actividad, y comparte sus ids con todos los usuarios. Cada iteración crea un proceso con nombre único (marca de tiempo, hilo y contador) y mueve la actividad a coordenadas aleatorias (X de 0 a 600, Y de 0 a 200).

Configuración del script / enlace: plan thymeleaf/src/test/jmeter/plan-carga.jmx del repositorio Proyecto1. Se parametriza con usuarios, rampa, repeticiones, correo, clave, host y port (por defecto localhost:8080). Cada petición tiene una aserción del código de respuesta (200 o 201) y el token se extrae con un JSON Extractor ($.token).

Procedimiento de ejecución:

  1. Compilar el backend: cd thymeleaf y ./mvnw -DskipTests package.
  2. Arrancar el backend con base limpia: java -Xmx1g -jar target/thymeleaf-0.0.1-SNAPSHOT.jar --spring.profiles.active=h2, con la variable DEMO_ADMIN_PASSWORD definida.
  3. Ejecutar cada escenario, por ejemplo E3: ./mvnw jmeter:configure jmeter:jmeter jmeter:results -Dcarga.usuarios=100 -Dcarga.rampa=30 -Dcarga.repeticiones=10 -Dcarga.clave=$DEMO_ADMIN_PASSWORD
  4. En paralelo, registrar CPU y memoria del proceso Java (una muestra por segundo).
  5. Revisar target/jmeter/reports/<fecha-hora>/plan-carga/index.html. Los cuatro escenarios se corrieron seguidos sobre la misma base, así que los datos creados se acumulan de uno a otro.

4. Resultados y análisis

Latencia media, p95 y p99: totales del reporte de JMeter. E1: media 10,6 ms, p95 15 ms, p99 97 ms; E2: media 7,3 ms, p95 9 ms, p99 94 ms; E3: media 6,9 ms, p95 12 ms, p99 93 ms; E4: media 83,2 ms, p95 320 ms, p99 583 ms. Hasta 100 usuarios el p99 total (cerca de 95 ms) lo marca el login; las demás operaciones tienen un p99 por debajo de 40 ms. El detalle por operación está en la tabla «Detalle por operación».

Solicitudes por segundo / throughput: 49,9, 91,6, 140,3 y 314,9 peticiones por segundo. El throughput crece casi en proporción a los usuarios: hasta 100 usuarios el servidor nunca fue el límite.

Tasa de errores: 0 % en los cuatro escenarios (22.594 peticiones). En una primera corrida aparecieron respuestas 400 «Ya existe un proceso llamado…» al crear procesos (y por eso también en el detalle): el script repetía nombres entre corridas y el backend aplicó bien la regla de nombre único por empresa. Se corrigió el script y se repitieron todos los escenarios sobre una base limpia.

Consumo de CPU y memoria: CPU del proceso Java, como porcentaje de toda la máquina: promedio 8 %, 10 %, 9 %, 31 % y picos 33 %, 41 %, 33 %, 73 % (E1 a E4). Memoria (working set): promedio entre 161 y 203 MB, con un pico de 645 MB en E4, por debajo del límite de 1 GB; no hubo errores de memoria.

Cuellos de botella identificados:

  • Login: BCrypt tarda unos 94 ms por petición con poca carga y sube a 186 ms de mediana (p95 659 ms) con 200 usuarios. Es un costo de CPU intencional por seguridad; se mitiga porque cada usuario hace login una vez y reutiliza el JWT durante 60 minutos.
  • GET /api/v1/procesos no está paginado: devuelve todos los procesos de la empresa, que durante E4 pasó de unos 1.700 a 3.700 procesos. Fue la operación más lenta (p95 385 ms, máximo 1,6 s) y movió unos 21 MB/s, frente a menos de 120 KB/s de las demás. El listado paginado (/buscar) responde mejor con el mismo volumen.
  • Saturación a 200 usuarios: el p95 pasa de unos 10 ms a 320 ms sin errores. Las peticiones esperan turno en los hilos de Tomcat y en la CPU, que JMeter usaba al mismo tiempo.

5. Cierre

Comparación con criterios de aceptación: se cumplen en los cuatro escenarios, incluido el de estrés. El p95 más alto por operación fue 385 ms (listar, E4) y el del login 659 ms, ambos bajo su umbral; 0 % de errores; CPU promedio máxima de 31 %. Aviso: en E4 el p99 de las operaciones de negocio (entre 514 y 643 ms) ya pasa de 500 ms, señal de que cerca de 200 usuarios simultáneos empieza la degradación en este equipo.

Acciones de mejora:

  • Que el frontend use el listado paginado, o paginar GET /api/v1/procesos: es la operación con más latencia y volumen.
  • Repetir la prueba contra el despliegue en Kubernetes con PostgreSQL 16 y JMeter en otra máquina, para medir el ambiente real.
  • Agregar al plan otras acciones del editor (crear arcos y gateways, reordenar lanes) y una prueba de duración de 15 a 30 minutos.
  • Correr el plan en GitHub Actions con un umbral de p95 que haga fallar el pipeline.

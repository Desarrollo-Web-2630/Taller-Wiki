1. Alcance técnico

Componentes frontend cubiertos: 4 archivos de prueba (api.interceptor.spec.ts, auth.guard.spec.ts, invitado.guard.spec.ts y rol.guard.spec.ts) con 17 casos en Karma/Jasmine.

  • El frontend Angular (repositorio Proyecto2) tiene 17 pruebas unitarias (Karma/Jasmine) para guards e interceptor, pero no se analiza en SonarQube Cloud. Las cifras de cobertura y los hallazgos de este documento corresponden al backend (Proyecto1); el recuento de pruebas incluye ambos repositorios cuando se indica.
  • Las reglas de negocio, la validación de datos y la seguridad están en el backend. El frontend presenta la información y consume la API REST. Sus guards ocultan pantallas según el rol y la compartición del proceso, pero no protegen nada por sí solos: cada petición se valida en el servidor con Spring Security.
  • Además de las 17 pruebas unitarias, el funcionamiento del frontend se valida con pruebas de extremo a extremo (E2E), descritas en el documento de Pruebas automatizadas.

Componentes backend cubiertos: Todo el backend Spring Boot del repositorio Proyecto1 (módulo thymeleaf), con 45 clases de prueba y 401 casos en el estado actual, organizadas igual que el código fuente:

  • services: EmpresaService, UsuarioService, VerificacionCorreoService, CorreoService, ProcesoService, ActividadService, GatewayService, ArcoService, ElementoConectableService, RolProcesoService, PoolService, LaneService, MensajeService, AuditoriaService, AccesoProcesoService, ComparticionService y PermisoPoolService, además de UsoRolProcesoConLanes y UsoRolProcesoSinLanes en pruebas.
  • controllers: un @WebMvcTest por controlador REST, incluidos los nuevos HistorialController, ComparticionController y PermisoPoolController (estos tres agrupados en NovedadesControllerTest), más GlobalExceptionHandler.
  • repository: ProcesoRepository (consultas personalizadas con filtro por empresa).
  • dto, model, util y config: DTO de petición y respuesta, entidades, PasswordUtil, EmpresaActual, DataInitializer y la configuración de OpenAPI.
  • security (2 clases): JwtServicioTest (9 casos: generar y validar el token, token alterado, vencido, firmado con otra clave y revocación) y SeguridadIntegracionTest (integración: 22 casos de login, respuestas 401 y 403 por rol, aislamiento entre empresas y CSRF).

Frameworks de prueba y versiones: Java 17 y Spring Boot 3.3.2. Las versiones de las librerías de prueba las fija el BOM de Spring Boot:

  • spring-boot-starter-test: JUnit 5 (Jupiter), Mockito, AssertJ y Spring Test (MockMvc).
  • spring-security-test y JJWT 0.12.6 para las pruebas de autenticación con JWT y autorización por rol.
  • H2 en memoria (perfil h2) para las pruebas de repositorio.
  • JaCoCo 0.8.12 (jacoco-maven-plugin) para el reporte de cobertura.
  • SonarScanner para Maven 3.11.0.3922 (sonar-maven-plugin). Frontend: Karma y Jasmine con ChromeHeadless, 17 casos en 4 archivos .spec.ts.

Estrategia de mocks / fixtures: Se usa un tipo de aislamiento según la capa:

  • Servicios: @ExtendWith(MockitoExtension.class) con @Mock para repositorios y servicios colaboradores, y @InjectMocks para la clase probada. No se levanta Spring ni base de datos.
  • Controladores: @WebMvcTest con MockMvc y @MockBean del servicio. Se verifican el código HTTP, el JSON de respuesta y el manejo de errores.
  • Repositorio: @DataJpaTest con perfil h2. En @BeforeEach se crean dos empresas (A y B) con sus procesos para comprobar que las consultas nunca mezclan empresas.
  • Correo: JavaMailSender simulado con Mockito; en las pruebas no se envía ningún correo real.
  • DTO, modelo y utilidades: pruebas puras de JUnit, sin contexto de Spring.

2. Pruebas unitarias

Criterios de selección de unidades: Se priorizó la capa de servicio porque ahí viven las reglas de negocio de las historias de usuario. Para cada regla se escribió un caso válido y uno o más casos de error. Las reglas cubiertas son:

  • Validaciones de datos (NIT, correo, contraseña, campos obligatorios).
  • Unicidad dentro de la empresa (NIT, nombre de proceso, nombre de rol).
  • Aislamiento multiempresa: ninguna operación devuelve ni modifica datos de otra empresa.
  • Coherencia del diagrama: los arcos no cruzan pools, los mensajes sí; no se elimina un rol en uso ni un pool con lanes.
  • Ciclo de vida del proceso: borrador, publicado e inactivo (eliminación lógica).
  • Además se probaron los controladores (contrato HTTP), las consultas propias del repositorio y PasswordUtil, por ser código sensible de seguridad.

Casos representativos: La tabla "Casos unitarios" resume 17 de los 401 casos, uno o dos por regla de negocio. Los nombres de los métodos de prueba siguen el patrón metodo_escenario_resultadoEsperado, por ejemplo crearArco_entreActividadesDeDistintoPool_lanzaExcepcion.

Comandos para ejecutar pruebas: Desde la carpeta thymeleaf del repositorio Proyecto1 (en Windows se usa mvnw.cmd):

./mvnw test                          # todas las pruebas + reporte JaCoCo
./mvnw test -Dtest=EmpresaServiceTest  # una sola clase
./mvnw verify sonar:sonar -Dsonar.projectKey=Desarrollo-Web-2630_Proyecto1 \
  -Dsonar.token=$SONAR_TOKEN           # análisis en SonarQube Cloud
  • El reporte de cobertura queda en target/site/jacoco/index.html, y el XML que lee SonarQube Cloud en target/site/jacoco/jacoco.xml.

Resultados, cobertura y exclusiones justificadas: El backend tiene 401 casos de prueba en 45 clases y el frontend 17 casos en 4 archivos; todas las pruebas pasan en la corrida actual. La última corrida analizada en SonarQube (commit b6dfca83) también terminó con todas las pruebas en verde: mvn verify habría fallado y no se habría generado el análisis si alguna prueba fallara.

9. Detalle de fallos y correcciones: H-05 (CSRF)

Qué reporta SonarQube: la regla java:S4502 marca cualquier configuración que deshabilite la protección CSRF de Spring Security y pide confirmar que es seguro. Tiene severidad High en seguridad y antes se clasificaba como Security Hotspot (etiqueta former-hotspot). Ver figura 7.

Por qué aparece: al integrar Spring Security en la entrega final, SecurityConfig deshabilita CSRF con .csrf(AbstractHttpConfigurer::disable).

Por qué es seguro en este proyecto: un ataque CSRF aprovecha que el navegador envía por su cuenta las cookies de sesión cuando otro sitio dispara una petición. En esta API eso no puede pasar:

  • La API es sin estado (SessionCreationPolicy.STATELESS): no crea sesión ni cookie JSESSIONID.
  • La única forma de autenticarse es el JWT en el encabezado Authorization: Bearer. El navegador nunca agrega ese encabezado por su cuenta; solo lo pone el interceptor de Angular.
  • El frontend guarda el token en sessionStorage, no en una cookie.
  • CORS solo admite los orígenes de APP_CORS_ORIGENES y los encabezados Authorization y Content-Type.

Por qué no se activó CSRF: activarlo obligaría a manejar un token CSRF adicional en cada petición sin agregar protección real, porque ninguna petición se autentica con cookies.

Corrección aplicada:

  • Comentario en SecurityConfig que deja documentada la revisión y remite a las pruebas.
  • Tres pruebas en SeguridadIntegracionTest: csrf_elLoginNoCreaSesionNiCookie (el login no devuelve Set-Cookie), csrf_peticionConCookieDeSesionPeroSinToken_responde401 y csrf_tokenEnviadoComoCookie_noAutentica (un token enviado como cookie no autentica).
  • En SonarQube Cloud el issue se marcó como aceptado (Accepted) el 16/11 con la justificación anterior como comentario. Desde entonces el proyecto tiene 0 issues de seguridad y rating A (figura 9).

Estado: cerrado por revisión. Si en el futuro la autenticación pasara a usar cookies, habría que volver a activar CSRF.

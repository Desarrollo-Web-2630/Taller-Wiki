1. Vista general

Objetivo del documento: describir la arquitectura del Sistema de Gestión de Procesos con el modelo C4, desde el contexto (quién usa el sistema y con qué se comunica) hasta el código de un módulo, y dejar registradas las decisiones de diseño y sus compromisos. Todo lo descrito corresponde al código de la rama main de los dos repositorios (backend y frontend) y a los manifiestos con los que se despliega en MicroK8s.

Principales decisiones arquitectónicas: el sistema se divide en una SPA y una API REST independientes, cada una con su repositorio, su imagen Docker y su despliegue. Las decisiones que más pesan son:

  • Cliente-servidor con SPA + API REST: Angular en el navegador y Spring Boot como backend, comunicados por JSON.
  • Arquitectura en capas en el backend: Controller → Service → Repository → Entity, con DTOs en la frontera de la API.
  • Seguridad sin estado: Spring Security con JWT firmado (HMAC-SHA256); no hay sesión en el servidor.
  • Aislamiento multiempresa: la empresa del usuario se toma del token ya validado y filtra todas las consultas.
  • Borrado lógico: ningún registro se borra físicamente (@SQLDelete + @SQLRestriction sobre el campo status).
  • Despliegue en Kubernetes: GitHub Actions construye las imágenes, las publica en GHCR y un runner self-hosted las aplica en MicroK8s detrás de un único Ingress.

Tecnologías y versiones utilizadas:

  • Backend: Java 17, Spring Boot 3.3.2 (Web, Data JPA, Validation, Security, Mail), Hibernate, jjwt (JWT), ModelMapper 3.1.1, Lombok, springdoc-openapi 2.6.0 (Swagger).
  • Frontend: Angular 20.3, TypeScript 5.9, RxJS 7.8, componentes standalone con signals; ESLint (angular-eslint 20.7) y Karma/Jasmine para pruebas.
  • Persistencia: PostgreSQL 16 en despliegue; H2 en memoria para desarrollo y pruebas.
  • Servidor web: nginx 1.27 (alpine) para servir la SPA y reenviar /api al backend.
  • Contenedores y despliegue: Docker (builds multietapa), Docker Compose en local, MicroK8s 1.30 con NGINX Ingress, GitHub Container Registry (GHCR) y GitHub Actions.
  • Calidad y pruebas: JUnit 5 y Spring Security Test, JaCoCo 0.8.12, SonarQube (sonar-maven-plugin), JMeter (jmeter-maven-plugin 3.8.0), Postman.

2. Nivel 1 - Contexto

Actores externos: personas que usan el sistema desde el navegador. El rol de acceso (ADMIN, EDITOR, LECTURA) define qué puede hacer cada una dentro de su empresa:

  • Representante de empresa (visitante): registra la empresa con nombre, NIT y correo; el sistema crea su administrador inicial inactivo, que se activa con el enlace que llega por correo.
  • Administrador (ADMIN): gestiona usuarios, roles de proceso y los datos de la empresa; es el único que elimina, inactiva o reactiva procesos, los comparte con otras empresas y define qué roles de acceso pueden modificar cada pool.
  • Editor (EDITOR): crea y edita procesos y todo su diagrama: actividades, arcos, gateways, pools, lanes y mensajes.
  • Usuario de solo lectura (LECTURA): consulta procesos, diagramas, usuarios, roles e historial de su empresa, sin modificar nada. Cualquier usuario puede además ver, en solo lectura, los procesos que otra empresa compartió con la suya.

Sistemas externos: el único sistema externo real es el servidor de correo SMTP (por ejemplo Gmail, puerto 587 con STARTTLS), que entrega los correos de verificación y activación de cuenta. En el despliegue del curso el envío está desactivado (APP_MAIL_ENABLED=false) y el enlace se escribe en el log del backend. Los clientes, proveedores y sistemas externos que aparecen como pools en los diagramas BPMN solo se modelan: el sistema no se conecta a ellos, porque modela procesos pero no los ejecuta.

Descripción de interacciones: todas las personas acceden por HTTP desde el navegador, dentro de la red de la universidad o con su VPN. El visitante registra la empresa y recibe por correo el enlace para fijar la contraseña del administrador. Después cada usuario inicia sesión con correo y contraseña, recibe un token y con él trabaja solo sobre los procesos de su empresa y los que otras empresas le compartieron. Al cerrar sesión el token queda revocado. El sistema llama al servidor SMTP únicamente para enviar los enlaces de verificación.

3. Nivel 2 - Contenedores

Aplicación frontend: SPA en Angular 20 (repositorio Proyecto2, carpeta front/). Se compila a archivos estáticos que sirve nginx 1.27 en 2 réplicas; el mismo nginx reenvía /api/ al backend y agrega encabezados de seguridad (X-Content-Type-Options, X-Frame-Options, Referrer-Policy). En el navegador, un interceptor HTTP antepone /api a cada llamada, agrega Authorization: Bearer <token> y cierra la sesión si recibe un 401. Los guards authGuard, invitadoGuard y rolGuard controlan qué pantallas se ven; la sesión se guarda en sessionStorage. Las pantallas se cargan por módulo con lazy loading (procesos, usuarios, roles) e incluyen el editor del diagrama con arrastrar y soltar, la configuración para compartir procesos, los permisos por pool y el historial de cambios.

Servicios / backend: API REST en Spring Boot 3.3.2 con Java 17 (repositorio Proyecto1, carpeta thymeleaf/; el nombre viene de la plantilla inicial del proyecto, ya no usa vistas Thymeleaf). Expone /api/auth (login, activación y verificación de correo, logout) y /api/v1/... para empresas, usuarios, procesos, actividades, gateways, arcos, elementos, roles de proceso, pools, lanes, mensajes, compartición de procesos, permisos por pool e historial. Concentra la validación del modelo BPMN, la autenticación con JWT, los permisos por rol y el aislamiento por empresa. La documentación OpenAPI se genera sola en /swagger-ui.html. Corre en un pod con readiness y liveness probes sobre /v3/api-docs.

Persistencia y almacenamiento: PostgreSQL 16 en un pod propio (Deployment con estrategia Recreate) y un PersistentVolumeClaim de 1 Gi, para que los datos sobrevivan a reinicios. Las credenciales salen del Secret procesos-secrets y nunca se versionan. El backend accede con JPA/Hibernate; las tablas las crea y actualiza Hibernate (ddl-auto=update). Ningún registro se borra físicamente: cada tabla tiene status (0 activo, 1 borrado). Para desarrollo se usa H2 en memoria (perfil h2). El respaldo se hace con pg_dump sobre el pod (ver DESPLIEGUE_K8S.md).

Integraciones:

  • SPA → API: JSON sobre HTTP con JWT en el encabezado Authorization, a través de nginx (mismo origen, sin CORS en despliegue).
  • Ingress NGINX de MicroK8s: entrada única por la IP de la VM (10.43.99.75); /api, /swagger-ui y /v3/api-docs van al Service procesos-backend:8080, /wiki y /api/wiki a la wiki del proyecto (procesos-wiki:8080, Ingress propio) y el resto a procesos-frontend:80.
  • API → PostgreSQL: JDBC al Service procesos-db:5432.
  • API → SMTP: JavaMailSender (spring-boot-starter-mail), opcional según APP_MAIL_ENABLED.
  • CI/CD: GitHub Actions publica las imágenes ghcr.io/<owner>/procesos-backend y procesos-frontend (tags latest y el SHA corto del commit) y el runner self-hosted las aplica con kubectl.

4. Nivel 3 - Componentes

Contenedor seleccionado: API REST (Spring Boot). Es el contenedor que concentra las reglas de negocio, la seguridad y el acceso a datos.

Componentes internos y responsabilidades:

  • Cadena de seguridad (SecurityConfig, JwtFiltro): API sin estado, CSRF desactivado (solo acepta el token en el encabezado), CORS por lista de orígenes y reglas por método y ruta: GET para cualquier rol; POST/PUT de modelado para ADMIN y EDITOR; DELETE, usuarios, empresa y roles solo ADMIN.
  • JwtServicio: genera y valida tokens HMAC-SHA256 con identificador único (jti), correo, usuarioId, empresaId, rol y vencimiento (60 minutos por defecto). Al cerrar sesión guarda el jti en TokenRevocado y desde ese momento rechaza el token.
  • UsuarioDetallesServicio: carga el usuario y su rol desde la base; un usuario desactivado pierde el acceso aunque su token siga vigente.
  • AuthController: login con BCrypt, logout (revoca el token), /api/auth/yo, activación de cuenta, verificación y reenvío del correo (máximo 3 por hora).
  • Controladores REST: un @RestController por recurso; reciben DTOs validados con @Valid y responden con ResponseEntity (201 al crear, 204 o 200 al eliminar).
  • EmpresaActual: entrega la empresa y el usuario de la petición a partir del token, nunca de un dato que envíe el cliente.
  • AccesoProcesoService: decide si la empresa puede leer o escribir un proceso: los propios con permiso completo y los compartidos por otra empresa (ProcesoCompartido) solo en lectura.
  • AuditoriaService: guarda en HistorialCambio quién hizo cada creación, edición o borrado, sobre qué entidad y cuándo; lo consulta HistorialController.
  • Servicios de negocio (@Service, @Transactional): reglas del modelo BPMN, por ejemplo arcos sin self-loop ni duplicados y dentro del mismo proceso, nombres únicos por empresa, roles que no se eliminan mientras estén en uso en una lane.
  • CorreoService: envía el enlace de verificación o lo escribe en el log si el correo está desactivado.
  • Repositorios (Spring Data JPA): una interfaz por entidad, con consultas JPQL que filtran por empresa.
  • Modelo de dominio: entidades JPA Empresa, Usuario, Proceso, ElementoConectable (Actividad, Gateway), Arco, Pool, Lane, RolProceso, Mensaje, ProcesoCompartido, PermisoPool, HistorialCambio, TokenRevocado y VerificacionToken.
  • GlobalExceptionHandler (@RestControllerAdvice): traduce las excepciones a un cuerpo uniforme {timestamp, status, mensaje} con 400, 401, 403, 404, 405, 415 o 500, sin exponer trazas.

Relaciones y dependencias: cada petición pasa primero por la cadena de seguridad, que valida el token con JwtServicio y carga el usuario con UsuarioDetallesServicio. Si la ruta es pública sigue a AuthController; si no, llega al controlador solo cuando el rol alcanza. Los controladores piden la empresa a EmpresaActual y delegan en los servicios; los servicios verifican el acceso con AccesoProcesoService, registran cada cambio con AuditoriaService y usan los repositorios, que mapean las entidades a PostgreSQL. Las dependencias van siempre de arriba hacia abajo (un repositorio nunca llama a un servicio) y se inyectan por constructor, lo que permite probar cada capa con dobles de prueba.

5. Nivel 4 - Código (opcional)

Módulo o componente seleccionado: módulo de arcos (HU-11, HU-12 y HU-13), el que une los elementos del diagrama. Se eligió porque en él se ve la herencia polimórfica del modelo y las validaciones de coherencia del diagrama.

Diagrama o estructura de clases / módulos: Actividad y Gateway extienden la entidad abstracta ElementoConectable con herencia JOINED, así que un Arco tiene origen y destino de tipo ElementoConectable y puede unir cualquier combinación de actividades y gateways. ArcoController expone /api/v1/procesos/{p}/arcos y delega en ArcoService, que antes de guardar valida en validarExtremos que origen y destino existan, sean del mismo proceso, no sean el mismo elemento y que no exista ya un arco entre ese par. Al eliminar, advertenciaAlEliminar avisa si el destino queda sin entradas o el origen sin salidas. Si el origen es un gateway, condicionParaGateway quita la condición cuando es paralelo y la exige cuando es exclusivo o inclusivo. Antes de leer o escribir, ArcoService verifica el acceso con AccesoProcesoService, y cada cambio queda en el historial por medio de AuditoriaService. ArcoRepository consulta siempre por empresa (findByIdAndProcesoEmpresaId), de modo que una empresa no puede leer ni modificar arcos de otra.

6. Decisiones y atributos de calidad

Seguridad y control de acceso

  • Contraseñas con BCrypt; el administrador inicial nace inactivo con una contraseña aleatoria y se activa con un token de un solo uso que vence en 24 horas.
  • JWT firmado con una clave de mínimo 32 caracteres guardada en el Secret de Kubernetes (JWT_SECRET); el login fallido responde 401 con un mensaje genérico que no revela si el correo existe; el logout revoca el token aunque no haya vencido.
  • Autorización por rol en SecurityConfig (compartir procesos y definir permisos de pool solo ADMIN) y aislamiento por empresa en cada consulta; los procesos compartidos se ven en solo lectura; el frontend oculta botones según el rol, pero quien decide es siempre el backend.
  • Credenciales de base de datos y de la aplicación solo en variables de entorno y Secrets; nunca en el repositorio.
  • El detalle de roles y pruebas de seguridad está en el documento "Roles y seguridad".

Escalabilidad y rendimiento

  • La API no guarda sesión: cualquier réplica puede atender cualquier petición mientras compartan el mismo JWT_SECRET, así que el backend se puede escalar con kubectl scale. Hoy corre con 1 réplica; el frontend corre con 2.
  • Requests y limits de CPU y memoria en cada Deployment (backend 384–768 Mi, JVM con MaxRAMPercentage=75) y probes que sacan del Service a un pod que no responde.
  • Listados paginados (page/size, tamaño máximo 100) y relaciones JPA con carga LAZY para no traer datos que no se usan.
  • Costo conocido: revisar si un token fue revocado es una consulta a la base en cada petición; los tokens vencidos se borran de esa tabla al revocar uno nuevo.
  • Límite conocido: PostgreSQL es una sola instancia con disco ReadWriteOnce; es el punto que no escala horizontalmente. Las mediciones están en el documento "Pruebas de carga" (plan JMeter en src/test/jmeter/plan-carga.jmx).

Mantenibilidad

  • Capas y paquetes separados por responsabilidad (controllers, services, repository, model, dto, security, config, util) y una carpeta por funcionalidad en el frontend, con su propio archivo de rutas.
  • DTOs en la frontera de la API: cambiar una entidad no rompe el contrato con el frontend.
  • Cerca de 360 casos de prueba en el backend (servicios, controladores, seguridad, modelo) y pruebas de guards e interceptor en el frontend; cobertura con JaCoCo y análisis con SonarQube.
  • Calidad en el frontend con ESLint (prohíbe any, fetch y axios) y un servidor mock (npm run mock) para trabajar sin backend.
  • Historial de cambios por entidad (quién, qué y cuándo) que sirve para auditar y para depurar.
  • Documentación de la API generada desde el código (Swagger), guía de despliegue versionada en DESPLIEGUE_K8S.md y wiki del proyecto en /wiki.

Justificación de decisiones y compromisos: se priorizó separar responsabilidades para que cada parte cambie sin afectar a las demás, idea central del curso. Los compromisos aceptados son: para poder revocar el JWT al cerrar sesión, cada petición consulta la tabla de tokens revocados, lo que hace la API un poco menos "sin estado"; el borrado lógico obliga a validar la unicidad de nombres en el servicio y no con restricciones de la base; la herencia JOINED agrega joins al consultar elementos a cambio de no tener columnas nulas; y una base de datos única simplifica la operación del curso a costa de no tener alta disponibilidad. La tabla de decisiones resume cada una.

Decisiones arquitectónicas

ID Decisión Alternativa Justificación
AD-01 SPA en Angular y API REST en Spring Boot, en repositorios y despliegues separados Vistas server-side con Thymeleaf (usadas al inicio del semestre) Desacopla interfaz y lógica, permite desplegar y escalar cada parte por separado y es lo que pide la entrega 2
AD-02 Autenticación sin estado con JWT (HMAC-SHA256, 60 min) Sesión HTTP con cookie en el servidor Cualquier réplica atiende cualquier petición y no aplica CSRF; el logout revoca el token guardando su jti en la base
AD-03 Empresa y rol tomados del token validado (EmpresaActual) Encabezado X-Empresa-Id enviado por el cliente (usado en la entrega 2) El cliente no puede hacerse pasar por otra empresa; la única excepción son los procesos compartidos, en solo lectura
AD-04 Borrado lógico con @SQLDelete y @SQLRestriction Borrado físico de filas Regla del enunciado: conservar trazabilidad y auditoría; la unicidad se valida en el servicio
AD-05 Herencia JOINED en ElementoConectable (Actividad, Gateway) SINGLE_TABLE o TABLE_PER_CLASS Un arco une cualquier par de elementos sin columnas nulas ni repetidas; cuesta un join al consultar
AD-06 PostgreSQL 16 en producción y H2 en desarrollo MySQL Motor robusto y libre que el equipo usó desde el inicio; H2 permite arrancar y probar sin instalar nada
AD-07 Un único Ingress y nginx como proxy de /api (mismo origen) Exponer el backend aparte con NodePort y habilitar CORS Una sola dirección para todo el sistema y sin problemas de CORS en el navegador
AD-08 CI/CD con GitHub Actions → GHCR → runner self-hosted en MicroK8s Construir y desplegar a mano en la VM Cada push a main se despliega igual; las imágenes con el SHA del commit permiten volver a una versión exacta
AD-09 Validar las reglas del diagrama en el backend, no solo en el frontend Validar solo en la interfaz Cualquiera puede llamar la API con Postman; el backend es la única fuente de verdad
